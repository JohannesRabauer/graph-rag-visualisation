Trace replay

Replay walks through the retrieval trace one step at a time and lights up the entities, relationships and communities it touched on the canvas.

Overview

Open it from "Replay this answer's Retrieval Trace" under an answer. The close button on the scrubber ends it.

The idea

Explainability is a selling point of graph retrieval: the evidence path is a set of nodes and edges, so it can be shown rather than asserted.

In this demo

The scrubber fetches GET /api/traces/{traceId} and replays the RetrievalStep list of that RetrievalTrace. Each step has a kind (entity, relationship, community, passage, sub-question, synthesis, or the vector kinds), an identifier that matches a canvas element, and a label used for the caption. The caption wraps across the full width of the bar so long labels stay readable. Drift traces also show a phase badge and open the drift tree.

Passage steps

A cited answer's trace also records the source passages that were read, as passage steps. A passage is not a node on the graph, so its caption names it instead: "Read passage N of document", followed by the excerpt. The document and passage number come from the same text-unit endpoint the answer's Sources list uses. Until that lookup returns, or if it fails, the caption just says "Read passage" with the excerpt.

While a passage step is current, every entity that was extracted from that passage is highlighted on the canvas, the same way as a matched entity. So you can see which part of the graph the passage supports.

Traces are kept only in memory (RetrievalTraceStore); after a restart the replay link of an old answer no longer works.

Simplifications

  • A trace shows what was touched, not why it scored highest: scores are not recorded.
