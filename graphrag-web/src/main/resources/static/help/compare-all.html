Looking inside

Comparing all four retrieval methods

"Compare all four retrieval methods" answers your question again with Local, Global, DRIFT and Vector Search, one after the other on the same corpus. The Compare tab shows them as four columns over one evidence table. When an answer is wrong, you can trace the miss to the stage that caused it: retrieval, ranking or generation. Then you don't have to blame "the graph".

Overview

What runs

The button sends one POST /api/corpora/{corpusId}/compare-all. CompareAllModes runs the four methods one after the other, never in parallel, so their latencies do not compete for the same model or database. Every run gets its own clock (StageTiming): the LLM and embedding ports are wrapped so each call is timed and counted, and everything else (graph and vector store reads, ranking, context assembly) counts as retrieval. A method that fails does not stop the others; its column says it failed. Nothing is added to the chat: the button turns into a "Four-way comparison ready" link, and "Run again" repeats the whole comparison (four new runs, so live answers can change).

The four columns

  • Answer. Each method's answer with its [n] markers and Sources, or its no-answer reason. Long answers scroll inside the column.
  • Time. The total, a bar scaled to the slowest of the four runs, and the split into retrieval, embedding and LLM time with the number of calls. LLM time covers every model call of the run, so DRIFT's sub-question calls count here too.
  • Traversal. How many steps of each kind the method's trace has: entities, relationships, communities and passages read for the graph modes, sub-questions for DRIFT, retrieved chunks for Vector Search.
  • Replay. The usual trace replay of that run, step by step.

The evidence table

One row per passage that any method ranked, read into its context, or cited. Each method's cell says how far the passage got there:

  • cited [n]: the answer cites it.
  • in context: it was in the answer's context, but the answer does not cite it.
  • ranked #n · below cut-off: Vector Search scored it, but too low to be shown to the model (AnswerVectorBaseline keeps the top 5 of its ranking).
  • —: the method never reached it.

Vector Search cuts its own chunks, so a vector chunk joins the row of a passage a graph mode read when the chunk's text sits inside that passage (same document). Otherwise it gets a row of its own. Rows cited by more methods come first. Click a passage to read it in full.

Diagnosing a wrong answer

Read the passage that holds the right answer and mark it expected. Every column then names the stage where that passage got lost:

  • Retrieval: the method never reached the passage (the traversal didn't get there, or the passage was not in Vector Search's top 12).
  • Ranking: Vector Search found it, but ranked it below the cut-off.
  • Generation: the passage was in the context, but the answer ignored it, or the model said the context does not answer the question.
  • Evidence cited: the answer cites it. If that answer is still wrong, the model misread its own evidence.

The log

"Download log (JSON)" saves everything the view shows in one file: per method the answer, citations, every traversal step and the time split; the evidence table; and, when one is marked, the expected evidence with each method's diagnosis. The server also writes one compare-all log line per method with the same figures.

Simplifications

  • Without an OpenAI key the graph modes match keywords and read no passages, so only Vector Search fills the evidence table.
  • The expected evidence must be a passage some method reached. If no method reached it, that is a retrieval miss for all four.
  • The graph modes have no ranking cut-off of their own in this table; a passage they never read counts as a retrieval miss.
  • The summary line only states facts (who answered, fastest and slowest, shared citations); it does not judge which answer is right.
  • Without a key the deterministic stand-ins still count as calls, so an offline run can show "LLM 0 ms (1 call)".
  • Token usage per method is not shown.
