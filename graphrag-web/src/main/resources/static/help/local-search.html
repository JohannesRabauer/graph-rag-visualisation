Search mode

Local Search

Start at the one entity whose name best matches your question, take the single best relationship out of it, and answer from that hop.

Overview

Up to three trace steps: entity, relationship, entity; fewer when nothing matches or the seed has no matching relationship.

The idea

In canonical GraphRAG, local search finds entities related to the question, then gathers their neighbours, relationships and the source text chunks tied to them, and hands that context to an LLM to write the answer.

In this demo

AnswerLocalSearch scores every entity on name + type against the question words using KeywordMatcher (a substring hit is worth 2, a near-miss within a small edit distance is worth 1). The best entity is the seed. If nothing scores above zero, the answer is "no match" and the trace has zero steps.

It then looks only at relationships touching the seed, scores them the same way, and keeps the best one. The trace holds the seed, the relationship (identified as source->TYPE->target, the same id the canvas uses for its edges) and the entity on the other end. The answer is a sentence template filled with those names.

Replay highlights exactly this path on the canvas.

With a real embedding model configured (OPENAI_API_KEY set), the seeds are instead the three entities whose name: description is closest in meaning to the question, recorded as the first trace steps in similarity order, and the hop starts from the first; a corpus without entity embeddings, or the offline stub, falls back to the keyword match above.

With a real LLM configured (OPENAI_API_KEY set), the answer is written by the model instead of the template. The search gathers a small, bounded context and records each piece as a trace step as it goes: the seed entities with their descriptions, up to 10 relationships touching them (highest weight first), and up to 5 source passages (Text Units) those entities and relationships were extracted from, shown in the trace as TEXT_UNIT steps. The model sees every item numbered and must cite them inline as [n]. Only citations that point at a source passage are kept; they are renumbered from 1 and listed in the response's citations, so each [n] in the answer names a passage that is also a step of the same trace. If the model says the context does not answer the question, you get a plain "no answer" with the reason instead of a guess. If the model call fails, you see an error; nothing is retried and no template is passed off as the model's answer.

Simplifications

  • Offline (no key), Local Search is not LLM based: no source passages are read and the answer is a sentence template.
  • With a key, the context is a fixed-size slice (seeds, 10 relationships, 5 passages) rather than canonical GraphRAG's token-budgeted mix, and citation markers are shown as plain text.
  • Drift sub-questions and the synthesis are deterministic templates, not model output.
  • When an OPENAI_API_KEY is set, entity extraction, community summaries and Local answers are LLM-generated, and entity and community embeddings pick the search starting points by meaning. Without a key (offline), regex extraction and hashed bag-of-words embeddings stand in, and starting points are matched by keywords only.

So offline (keyword matching), a question that never names an entity finds nothing, however relevant the graph is.
