<intent-contract>

## Intent

**Problem:** `graphrag-core` is architecturally separable (framework-free, enforced by `maven-enforcer-plugin`), but "usable for other projects" has never been verified as a fact — no one has checked documentation, naming/branding, or actual publishability (GitHub #24).

**Approach:** Produce a written, evidence-based audit (a new markdown deliverable, not a code change) covering three areas — documentation, naming/branding, publishability — as a findings list (confirmed-solid vs. actually-missing) plus a prioritized punch list. Judgment calls this audit cannot make unilaterally (branding, whether "reusable" requires actually publishing) are surfaced as explicit open questions, not decided.

## Boundaries & Constraints

**Always:** Every finding must cite concrete evidence (a file, a count, a grep result) gathered by actually inspecting `graphrag-core` — never assert a gap without having checked for it. Present findings as confirmed-solid vs. actually-missing, not a single undifferentiated list. Surface the `com.graphraglens`-branding-vs-generic-identity question and the publish-or-not question as explicit open questions for the user, with the tradeoffs of each option stated — never pick one silently.

**Never:** Do not change any code, `pom.xml`, or add a README/`package-info.java`/LICENSE as part of this story — this story's own scope is the audit and punch list, not the fixes. Do not decide the two open judgment calls (branding; publish-or-not) — name them, don't answer them. File no follow-up story/issue yet — that happens only once the user has answered the open questions (a follow-up filed against unanswered questions could scope the wrong work).

</intent-contract>

- `graphrag-core/pom.xml` — no `<licenses>`/`<scm>`/`<developers>`/`<url>`, no source-jar/javadoc-jar plugin, no `<distributionManagement>` — zero publishing setup. Root `pom.xml` likewise: `groupId com.graphraglens`, `version 0.1.0-SNAPSHOT` (never released), no license metadata.
- Repository root — no `LICENSE` file anywhere in git history (`git log --all -- LICENSE` returns nothing). Root `README.md` (2421 bytes) documents the whole app (Docker Compose run instructions, module table) — it is not library documentation for `graphrag-core` on its own (no "add this as a dependency" instructions, no API usage example).
- `graphrag-core/src/main/java/com/graphraglens/core/` — no `package-info.java` in any of its three packages (`domain`, `port`, `usecase`).
- `graphrag-core/src/main/java/com/graphraglens/core/port/*.java` (the actual public API surface a consumer would call against) — 3 of 5 interfaces have class-level Javadoc (`DocumentParserPort`, `GraphStorePort`, `LlmPort`); `EmbeddingPort`, `VectorStorePort` have none. None of the 5 have method-level `@param`/`@return` Javadoc on their abstract methods.
- `graphrag-core/src/main/java/com/graphraglens/core/usecase/*.java` — all 15 classes have zero class-level Javadoc (0%). This is the layer a consumer would most need to understand to actually use the library.
- `graphrag-core/src/main/java/com/graphraglens/core/domain/*.java` — 10 of 14 classes have class-level Javadoc (71%); `Chunk`, `EmbeddedChunk` do not.
- `graphrag-core/src/test/java/...` — 11 test files covering most usecases (`AnswerDriftSearchTest`, `IngestCorpusTest`, `DetectCommunitiesTest`, etc.) — solid, confirmed-real test coverage, a genuine strength to note (not just a gap list).
- `maven-enforcer-plugin`'s `bannedDependencies` rule (`graphrag-core/pom.xml`) — verified real and effective (bans Spring/Neo4j-driver/LangChain4j groupIds at `validate` phase); the framework-free claim is enforced, not just asserted.

  - **No cross-module imports:** confirm (don't assume) that no class under `graphrag-core/src/main/java` imports anything from `com.graphraglens.adapter.*` or the web module's packages, and that the `maven-enforcer-plugin` `bannedDependencies` rule hasn't been bypassed via `<exclusions>` on any dependency anywhere in the reactor — state this as a verified fact with the actual command/grep used, not an assumption carried over from the rule merely existing.

  - **Javadoc-as-documentation sufficiency:** the test suite's own thoroughness doesn't answer whether a new consumer would still need worked usage examples on top of it — say so explicitly as its own finding, rather than treating "tests exist" as a closed question.
  - A brief mention (fold into the existing README/version punch-list items rather than a new one) of the module's JDK 25 requirement as a fact a `graphrag-core`-specific README should state explicitly, since the root README's mention of it doesn't count as `graphrag-core`'s own documentation.
