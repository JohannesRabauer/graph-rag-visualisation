- (version) Verified via web search (Sept 2026): Neo4j Community Edition supports exactly one standard database per DBMS; multi-database (one DB per tenant/corpus) is Enterprise-only. Source: neo4j.com/docs/operations-manual/current/database-administration/. Confirms corpus isolation must happen via a corpusId property scoping nodes within the single 'neo4j' database, never via separate per-corpus Neo4j databases.
- (constraint) Correctness gap found in existing AD-10/AD-11: Community.id is generated as a per-detection-run sequential string ('community-0', 'community-1', ...) in DetectCommunities.java, not globally unique -- two different corpora's communities would collide/MERGE onto the same node under AD-11's current {id, summary} key alone. Entity.normalizedIdentity() (lowercased name::type) is also plausibly repeatable across corpora (e.g. two corpora both mentioning 'Apple'). Both need corpusId folded into their Neo4j uniqueness/MERGE key, not just id/normalizedIdentity alone.
- (decision) AD candidate: Corpus registry (CorpusMeta) persistence stays confined to graphrag-adapter-neo4j -- a plain Spring-wired class there talks to Neo4j directly for registry reads/writes, called by graphrag-web -- but is NOT exposed as a new graphrag-core port. Reason: workflow status (BUILDING/READY/FAILED), activation history, and demo/offline flags are this app's own bookkeeping, not a GraphRAG-library concern; forcing every graphrag-core consumer to implement a CorpusRegistryPort they don't need would bloat the library's port surface. Keeps Neo4j driver code in exactly one module without expanding what a library consumer must implement.
- (decision) AD candidate: corpus activation is explicit, not inferred. A new POST /api/corpora/{corpusId}/activate endpoint is the only thing that updates a CorpusMeta's lastActivatedAt -- called once when the frontend's switcher selects a corpus, and once by the frontend on page load for whichever corpus GET /api/corpora's auto-restore logic picks. Query/vector-space/progress traffic never touches lastActivatedAt.
- (decision) AD candidate: Neo4j connectivity uses the plain org.neo4j.driver:neo4j-java-driver Maven artifact directly (not spring-boot-starter-data-neo4j, to avoid pulling in Spring Data Neo4j machinery this project has already rejected per AD-2) -- a single Driver bean is constructed from NEO4J_URI/NEO4J_USERNAME/NEO4J_PASSWORD env-backed properties (defaults bolt://neo4j:7687 / neo4j / graphraglens, matching docker-compose.yml's existing NEO4J_AUTH/NEO4J_PASSWORD), and driver.verifyConnectivity() is called at startup (ApplicationReadyEvent) so an unreachable Neo4j fails app startup with a clear error rather than degrading silently.
- (decision) AD candidate: every Neo4j node written by the graph/vector/registry adapters carries an explicit corpusId property, and every uniqueness constraint/MERGE key is scoped by it: Entity MERGE key is (corpusId, normalizedIdentity) not normalizedIdentity alone; Community MERGE key is (corpusId, id) not id alone (DetectCommunities generates sequential per-run ids like 'community-0' that would otherwise collide across corpora); Relationship MERGE key is (corpusId, source, type, target); CommunityMembership MERGE key is (corpusId, communityId, entityIdentity); CorpusMeta's own key is corpusId alone (it IS the corpus). Each gets a Neo4j uniqueness constraint on its composite key at startup/schema-init.
- (decision) AD candidate: startup reconciliation (any CorpusMeta still BUILDING transitions to FAILED) runs once via an ApplicationReadyEvent listener in graphrag-web, calling the corpus-registry class in graphrag-adapter-neo4j, before the app accepts traffic -- same startup sequencing point as the Neo4j connectivity check (connectivity check must succeed first, reconciliation runs immediately after).
- (version) Verified via web search (Sept 2026): Neo4j Community Edition supports native vector indexes with in-index filtering (available since 2026.01). As of Neo4j 2026.04, the old db.index.vector.queryNodes/queryRelationships procedures are deprecated in favor of the Cypher SEARCH clause -- docker-compose.yml pins neo4j:2026.08.1-community, so the Neo4j vector adapter must use the current SEARCH-clause syntax, not the deprecated procedures. Sources: neo4j.com/docs/cypher-manual/current/indexes/semantic-indexes/vector-indexes/, neo4j.com/blog/graph-database/community-edition/.
- (decision) AD candidate: chunk embeddings use exactly one native Neo4j vector index spanning all corpora's Chunk nodes (not one index per corpus, which would proliferate unboundedly as corpora accumulate under CAP-'retain indefinitely'), with corpusId used as an in-index filter predicate at query time via the current Cypher SEARCH clause. Chunk node MERGE key is (corpusId, chunk.id) per the earlier composite-key decision; ProjectionModel is stored as one (:ProjectionModel {corpusId, mean, pc1, pc2}) node per corpus, MERGE keyed on corpusId alone.
