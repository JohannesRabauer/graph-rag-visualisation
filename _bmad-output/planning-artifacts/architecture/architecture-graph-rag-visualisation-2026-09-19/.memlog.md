- (decision) [ADOPTED] Working mode: Fast path -- draft full spine with [ASSUMPTION] tags, user reviews once. Spine is the sole deliverable, no discussion doc/deck needed.
- (constraint) [ADOPTED from brief] Java-first implementation; Neo4j is the only graph store for v1; LangChain4j is the LLM orchestration layer specifically chosen to keep the LLM provider swappable; OpenAI is the initial provider.
- (constraint) [ADOPTED from brief addendum Notes for Architecture] File ingestion (text/PDF) needs a real parsing/extraction boundary isolated behind an interface, not a hardcoded loader. Provider abstraction must be an explicit architectural boundary. The 'library-in-mind' ambition means module boundaries should separate core GraphRAG/graph logic from the demo web app -- but no v1 feature should exist purely to serve that future-library goal.
- (constraint) [ADOPTED from PRD] Single-user, local-only, no auth/hosting/multi-tenancy. Docker Compose provisions Neo4j; OpenAI API key via env var only, no in-app config UI. No automatic retry/fallback for LLM failures -- errors must surface visibly, never crash/hang silently. Retrieval Trace is captured then replayed (not live-streamed).
- (constraint) [ADOPTED from PRD] 7 features / FR-1..FR-17: Document Ingestion (text/PDF/demo dataset), Knowledge Graph Construction (live LLM extraction into Neo4j), Community Detection & Visualization (Leiden clustering, toggle defaults ON first run), Query Interface (explicit Local/Global Search toggle), Retrieval Trace & Playback (captured, scrubbable replay), Setup & Deployment (Docker Compose + env var key), Graph Exploration (new: free-form pan/zoom/click explore page, always-on community view, node detail w/ connections+tags, read-only).
- (constraint) [ADOPTED from UX spines] Single-page main screen (chat + graph canvas + toggles + scrubber, no gated setup wizard) plus a second Explore page. Instrument visual direction: light-mode only, desktop/browser-only, no responsive/mobile requirement. No component library named in EXPERIENCE.md -- frontend framework choice is open.
- (version) Java 25 (current LTS, verified Sept 2026 web search). Spring Boot 4.1.1 / Spring Framework 7 (verified). LangChain4j 1.19.0 (verified) -- ships Neo4jEmbeddingStore, Neo4jText2CypherRetriever, and a KnowledgeGraphWriter+LLMGraphTransformer path purpose-built for LLM-driven graph construction from text; OpenAI is first-class. Neo4j 2026.06.0 current stable; GDS library ships Leiden as Cypher procedures, available in Community Edition (no Enterprise license needed), but Leiden requires UNDIRECTED relationships. Neo4j Java Driver 6.1.0. Apache PDFBox 3.0.8 current actively-maintained line.
- (decision) Web research recommends Spring Boot over Quarkus/Javalin for this project (best doc/library ecosystem fit incl. official LangChain4j and Neo4j Spring Boot starters; startup-time/footprint advantages of Quarkus don't matter for a solo local-only app).
- (decision) Web research recommends the plain Neo4j Java Driver + hand-written Cypher over Spring Data Neo4j -- SDN's OGM abstraction fights raw GDS procedure calls, Cypher traversal, and community-detection writes, which are core to this app.
- (decision) Web research recommends Cytoscape.js over vis-network/Sigma.js/Neovis.js for the frontend graph canvas -- its style-class system and compound-node support fit the custom visual states needed (traversed/active edges, community hulls, replay scrubbing) better than alternatives; graph scale here doesn't need Sigma's WebGL advantage.
- (decision) Paradigm: Hexagonal Architecture (Ports & Adapters). graphrag-core (domain use cases: ingest corpus, extract entities/relationships, detect communities, local search, global search, explore graph) depends only on its own port interfaces (LlmPort, GraphStorePort, DocumentParserPort) -- zero compile dependency on Spring, the Neo4j driver, or LangChain4j. This directly serves the brief's library-in-mind goal: graphrag-core is the extractable future library.
- (decision) AD candidate: Neo4j access only via plain Neo4j Java Driver + hand-written Cypher inside a Neo4jGraphStoreAdapter implementing GraphStorePort -- never Spring Data Neo4j/OGM anywhere in the codebase.
- (decision) AD candidate: LLM access only via LlmPort, implemented by a single LangChain4jAdapter (OpenAI configured through LangChain4j). No class outside that adapter references LangChain4j or OpenAI SDK types directly.
- (decision) AD candidate: relationships used for community detection are modeled/projected as UNDIRECTED for GDS Leiden calls (GDS Leiden requires undirected input) -- a real schema/adapter constraint, not just a library note.
- (decision) AD candidate: Retrieval Traces are transient, held in-memory per session/query (e.g. a simple in-process store keyed by answer id), never persisted into Neo4j -- keeps ephemeral UI-replay data out of the graph store.
- (decision) AD candidate: community detection (FR-6) always runs asynchronously immediately after graph construction completes, regardless of the main-screen visualization toggle (FR-7) -- the toggle gates only client-side animation/rendering, never whether/when detection itself runs.
- (decision) AD candidate: live ingestion/graph-construction progress (per EXPERIENCE.md's 'nodes/edges appearing as extracted') is pushed to the browser via Server-Sent Events (one-way server-to-client); WebSocket is not used since no client-to-server real-time channel exists anywhere in the app (Retrieval Trace replay is explicitly post-hoc, not live).
- (decision) AD candidate: Docker Compose deployment topology is exactly two services -- 'app' (Spring Boot, serves REST+SSE API and the built Cytoscape.js SPA as static resources from the same jar) and 'neo4j' (Community Edition with the GDS plugin enabled). No separate frontend container/dev-server in the compose file, to protect the one-command-setup requirement (PRD FR-14).
- (decision) AD candidate: document parsing (FR-1/FR-2, plain text + PDF via Apache PDFBox) sits behind DocumentParserPort with one adapter class per file type; adding a future file type (Non-Goal for v1) means adding an adapter, never touching graphrag-core ingestion use-case code.
- (assumption) [ASSUMPTION] Build tool: Maven multi-module (one module per hexagon ring: graphrag-core, graphrag-adapter-neo4j, graphrag-adapter-langchain4j, graphrag-adapter-parsing, graphrag-web) -- a reasonable, conventional default for a multi-module Java project; Gradle would work equally well, this is a low-stakes seed-level pick open to the user's preference.
- (assumption) [ASSUMPTION] Frontend build: a small TypeScript+Vite SPA using Cytoscape.js, built to static assets and copied into graphrag-web's src/main/resources/static at build time (via frontend-maven-plugin or a manual build step) -- keeps the two-container deployment (AD) without hand-authoring vanilla JS. Exact build wiring is implementation detail.
- (question) Open question: exact in-memory Retrieval Trace store implementation (simple ConcurrentHashMap in a Spring singleton bean vs. a small embedded cache library like Caffeine) -- low-stakes, left to implementation; noted as Deferred, not an AD, since either choice is compatible with AD-5 (transient, non-persisted) and a solo dev won't diverge from themselves.
- (direction) Deferred: authentication/authorization (explicit Non-Goal, PRD NFR single-user/local-only) -- would need a new architecture pass if ever added. Multi-tenancy / hosted deployment -- deferred, same reason. Support for graph databases other than Neo4j -- deferred (PRD Non-Goal). Formal retrieval-quality benchmarking/evaluation infrastructure -- deferred (PRD Non-Goal). Observability/monitoring beyond basic console/application logs -- deliberately out of scope for a solo local-only hobby app; revisit only if the library-extraction goal (brief Vision) becomes real and gains other users.
