topic: Wire real Neo4j-backed graph/vector store adapters and add durable multi-corpus history with a switcher UI
updated: 2026-09-28T18:08

- (note) User discovered restart loses all state (KG, embeddings, active corpus) and wants it wired to Neo4j properly, plus a corpus history/switcher, done thoroughly via BMAD.
- (note) Investigation finding: Neo4jGraphStoreAdapter and Neo4jVectorStoreAdapter (graphrag-adapter-neo4j) are empty compatibility-alias classes that just extend the in-memory adapters -- no Neo4j driver dependency exists in any pom, no Bolt connection, no Cypher anywhere in the codebase. 'Wiring to Neo4j' is net-new adapter implementation, not a bean swap.
- (note) docker-compose.yml already defines a healthy neo4j service (Community Edition + GDS plugin, per AD-8) and app depends_on it -- infrastructure has existed since Epic 1/2 but was never actually consumed by the adapters.
- (constraint) AD-1: graphrag-core stays framework-free -- no Neo4j driver import may appear anywhere in graphrag-core; all Bolt/Cypher code lives in graphrag-adapter-neo4j behind GraphStorePort/VectorStorePort.
- (constraint) AD-10: Entity writes must use Cypher MERGE keyed on normalized identity (lowercased name + entity type), never blind CREATE, so repeated extraction/re-ingestion doesn't duplicate nodes.
- (constraint) AD-11: Communities must be written as first-class (:Community {id, summary}) nodes related to member Entities via [:BELONGS_TO], not a scalar communityId property.
- (constraint) AD-8: deployment stays exactly two containers (app, neo4j) -- no third container (e.g. a separate SQLite/Postgres box) may be introduced for corpus registry metadata; it must live in Neo4j itself alongside the graph/vector data.
- (constraint) GraphStorePort/VectorStorePort already define corpusId-scoped methods (entities(corpusId), persistChunks(corpusId, ...), etc.) and InMemoryGraphStoreAdapter/InMemoryVectorStoreAdapter already implement per-corpus scoping correctly -- the new Neo4j adapters must satisfy the same per-corpus scoping contract (e.g. a corpusId property or relationship on every node/chunk), they are not adding multi-corpus support from scratch.
- (decision) Neo4j runs as the existing external docker-compose service (bolt://neo4j:7687 in-container / bolt://localhost:7687 from host), never embedded-in-JVM. Connection settings (uri, user, password) are added to application.yml as env-var-overridable properties, matching docker-compose.yml's existing NEO4J_AUTH/NEO4J_PASSWORD convention.
- (decision) Refinement of user's persistence-scope answer: rather than a second embedded store for corpus registry metadata, corpus metadata (id, name, document filenames, workflow status, createdAt, lastActivatedAt) is persisted as Neo4j nodes too (e.g. (:CorpusMeta)), so there is exactly one durable store and AD-8's two-container rule is never at risk. Flagged to user as a refinement of their original choice, not a silent override.
- (decision) Full history + switcher UI is in scope (user's explicit choice): a new GET /api/corpora list endpoint backed by CorpusMeta nodes, and frontend UI listing past corpora with name/status/createdAt, clickable to reassign the frontend's activeCorpusId and re-render graph/vector-space/query panels against the selected corpusId -- query/vector-space/progress endpoints are already corpusId-scoped per-request so no backend change is needed there beyond the list endpoint.
- (decision) On startup, the app auto-restores the most-recently-activated corpus as the active one (reads lastActivatedAt off CorpusMeta nodes) so the user lands on their last work without manual re-selection, while the history list remains available to switch to any other retained corpus.
- (decision) All corpora ever ingested are retained in Neo4j indefinitely (user's explicit choice) -- no automatic pruning/retention policy in this spec. Deleting a corpus, if ever added, is a future capability, not this one.
- (capability) CAP-1 Neo4j graph-store adapter: intent - the app persists a corpus's extracted Entities, Relationships, Communities, and CommunityMemberships to the running Neo4j instance instead of JVM heap, scoped per corpusId, via a real GraphStorePort implementation using the Neo4j Java driver / Cypher (MERGE per AD-10, Community nodes per AD-11). success - after ingesting a corpus, querying Neo4j Browser directly (or a GDS Leiden community-detection run) against that corpusId shows the same Entity/Relationship/Community nodes the app's UI displays, and they are still present after restarting the app container without re-ingesting.
- (capability) CAP-2 Neo4j vector-store adapter: intent - the app persists a corpus's embedded chunks and fitted 2D projection model to Neo4j instead of JVM heap, scoped per corpusId, via a real VectorStorePort implementation. success - after ingesting a corpus and restarting the app, the vector-space view and AnswerVectorBaseline query mode for that corpusId work identically to before the restart, with no re-embedding.
- (capability) CAP-3 Neo4j connection configuration: intent - the app connects to the docker-compose neo4j service using externally configurable bolt URI/credentials, and fails fast with a clear startup error if Neo4j is unreachable rather than silently falling back to in-memory. success - starting the app stack via docker-compose (as AD-8 defines it) requires no manual connection setup; stopping the neo4j container and starting the app alone produces an explicit connection-failure log/error, not silent degraded behavior.
- (capability) CAP-4 Durable corpus registry: intent - corpus bookkeeping (id, derived name, document filenames, workflow status BUILDING/READY/FAILED, offline flag, createdAt, lastActivatedAt) is written to Neo4j as CorpusMeta nodes at the same lifecycle points CorpusStore currently updates in-memory maps, so the registry itself survives restart. success - after restarting the app, previously-ingested corpora still appear with their correct name and status, without needing to be re-uploaded.
- (capability) CAP-5 Auto-restore last active corpus on startup: intent - on app startup, the frontend's activeCorpusId is automatically set to whichever corpus has the most recent lastActivatedAt, so the user sees their last-worked-on corpus without manual selection. success - stopping and restarting the whole docker-compose stack (app + neo4j) reopens the UI already pointed at the same corpus and its graph/vector-space that was active before the restart.
- (capability) CAP-6 Corpus history list endpoint: intent - a new GET /api/corpora endpoint returns all retained corpora (id, name, status, createdAt, lastActivatedAt) sourced from CorpusMeta nodes, ordered most-recently-activated first. success - calling GET /api/corpora after ingesting three corpora across two app restarts returns all three with correct metadata.
- (capability) CAP-7 Corpus switcher UI: intent - the frontend renders the corpus history from CAP-6 as a selectable list; clicking an entry reassigns activeCorpusId to that corpus and re-renders the graph canvas, vector-space view, and query panel against it, and records that corpus's lastActivatedAt as now. success - with two previously-ingested corpora, clicking the non-active one in the UI swaps the displayed graph/vector-space/query results to that corpus's data within the same page load, no re-ingestion or full page reload required.
- (note) Non-goal: original uploaded document bytes are not retained anywhere -- per user's persistence-scope choice, a corpus cannot be rebuilt/re-ingested from scratch after restart, only its already-extracted graph/vectors/metadata are restored.
- (note) Non-goal: no corpus deletion/retention-pruning capability -- all corpora are kept indefinitely per user's explicit choice; a delete capability is future work.
- (note) Non-goal: no embedded/in-process Neo4j -- only the existing external docker-compose neo4j service is supported.
- (note) Non-goal: NFR3 (single-user, local-only, no auth/multi-tenancy) is unchanged -- multi-corpus history is not multi-user; it's one user's own corpora.
- (note) Non-goal: RetrievalTrace/replay (AD-5, FR-12-13) stays in-memory as today -- persisting query trace history is a separate, unaddressed feature, not part of this spec.
- (note) Non-goal: no data-migration tool for pre-existing in-memory corpora -- since nothing survives a restart today, there is nothing to migrate; this spec only affects corpora ingested after it ships.
- (note) Success signal: a user ingests two corpora, restarts the full docker-compose stack, and on reopening the app is looking at the same corpus (graph, vector-space, query answers) that was active before restart, with the other corpus one click away in a history list showing both -- with zero re-ingestion and zero LLM/embedding calls re-run.
- (question) Open question: should CorpusStore stay as an in-memory read cache in front of the new Neo4j-backed registry (for low-latency SSE progress updates during active BUILDING), or be replaced outright by direct Neo4j reads/writes? Affects CAP-1/CAP-4 implementation shape; recommend resolving in the architecture pass.
- (question) Open question: what should a corpus's status show on restart if the app crashed mid-BUILDING (never reached READY or FAILED)? Needs a defined terminal state (e.g. auto-marked FAILED/STALE on startup) so the history list never shows a permanently-stuck BUILDING entry with no way to retry.
- (question) Open question: for offline/demo corpora (CorpusStore.markOffline, Story 9.1), should the offline flag also persist to Neo4j as CorpusMeta data, or should demo corpora be excluded from durable history entirely?
